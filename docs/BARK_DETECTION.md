# 狗叫声检测与声学智能方案

## 1. 目标

PetDaily 后续加入「狗叫监听」能力：主人把手机放在家中并保持应用运行，系统在本地持续分析麦克风输入，检测到疑似狗叫时自动记录事件，并把短音频、声学特征、上下文和主人反馈沉淀为可学习的数据。

第一阶段目标不是直接“读懂狗”，而是建立可校准的数据闭环：

- 自动发现：检测疑似狗叫片段，减少手动记录。
- 可回放：保存短音频片段和发生时间，方便主人确认。
- 可标注：主人给每次狗叫标注原因，例如无聊、想出去、想吃、害怕、寻求关注、未知。
- 可学习：持续积累音频向量、环境上下文和主人反馈，为后续个性化模型做训练数据。

## 2. 平台约束

当前 PetDaily 是 Next.js + Cloudflare 的 Web/PWA 形态，适合先做「前台监听」：

- 麦克风权限需要 HTTPS 和用户授权；本地开发可用 localhost，线上必须走 HTTPS。
- Web Audio 可以在前端做实时波形、频谱和能量分析。
- MediaRecorder 可以在检测到候选狗叫时保存短音频片段。
- Screen Wake Lock 可尝试保持屏幕不熄灭，但不同系统和浏览器支持不完全一致。
- 手机锁屏、浏览器进入后台、微信内置浏览器切走时，网页不能可靠保证持续录音。

因此第一版产品文案必须明确：网页模式下需要保持 PetDaily 在前台运行；如果未来要真正无人值守、锁屏后台长期监听，需要做原生 App、Expo/React Native 壳，或使用固定家用采集设备。

参考资料：

- MDN `getUserMedia()`：https://developer.mozilla.org/docs/Web/API/MediaDevices/getUserMedia
- MDN `AnalyserNode`：https://developer.mozilla.org/en-US/docs/Web/API/AnalyserNode
- MDN MediaStream Recording API：https://developer.mozilla.org/en-US/docs/Web/API/MediaStream_Recording_API
- MDN Screen Wake Lock API：https://developer.mozilla.org/docs/Web/API/Screen_Wake_Lock_API
- WebKit WebRTC / Media Capture：https://webkit.org/blog/7726/announcing-webrtc-and-media-capture/

## 3. V1 功能设计

### 3.1 监听工作台

新增「监听」入口，提供一个专门页面：

- 开始监听 / 停止监听。
- 麦克风权限状态。
- 当前环境音量、疑似狗叫强度、最近一次触发时间。
- 屏幕保持唤醒开关。
- 本地灵敏度滑杆：低 / 中 / 高。
- 今日检测次数、已确认狗叫、误报次数。

当前 V2 实现状态：

- 已新增「监听」页。
- 已接入前台麦克风监听、环境响度、噪声基线和疑似狗叫强度。
- 已接入 Screen Wake Lock 尝试保持屏幕唤醒。
- 已提供降误报 / 均衡 / 多收集三档灵敏度，默认优先减少人声和稳定噪音误触发。
- 已用 `MediaRecorder` 保存候选短音频片段，并在页面内提供单播放器回放和简易波形。
- 已新增声音库、叫声段合并和自动聚类，主人可以给一组相似声音批量校准。
- 已明确不保存全天录音，当前只保存候选短片段、声学摘要、embedding 和聚类标签。

### 3.2 狗叫事件流

检测到疑似狗叫时，写入时间线事件：

- 类型：`BARK`。
- 标题：疑似狗叫。
- 时间：触发时间。
- 数值：持续秒数、峰值响度、置信度。
- 附件：短音频片段 URL 或本地待上传状态。
- 备注：自动生成上下文，例如“晚饭后 42 分钟”“距离上次外出 3 小时”。

当前 V2 不保存全天音频，避免数据量过大和隐私风险。它保存的是：

- 触发时间。
- 候选短音频片段：线上建议进入 Cloudflare R2；本地开发可用 Data URL 验证。
- 声学摘要：响度、峰值、频谱中心、高频占比、频谱变化、过零率、频谱平坦度。
- embedding 向量：只由声学特征组成，用于按声音形态做相似度聚类。
- 时间上下文：小时、距上次饮食、距上次如厕、近 1 小时记录数量，保留给后续原因解释，不参与聚类。
- 叫声段：30 秒内连续触发会合并为一个 `BarkSession`，内部保留最多 6 段代表片段和估计叫声次数。
- 聚类结果：样本所属声音组、检测分数、声学画像、待确认/已确认/误报状态。

### 3.3 主人反馈

每条狗叫记录支持快速校准：

- 是狗叫 / 不是狗叫。
- 原因标签：无聊、想出去、想吃、害怕、寻求关注、玩耍兴奋、未知。
- 处理动作：喂食、出门、陪玩、安抚、忽略、其他。
- 处理后是否停止：是 / 否 / 不确定。

这些反馈比一开始追求复杂模型更重要，是后续个性化判断的核心训练数据。

当前 V2 的自学习方式：

- 浏览器端先提取候选片段特征，服务端把样本和音频索引写入 D1/R2。
- 每次新狗叫会把声学 embedding 和历史聚类中心做相似度计算。
- 相似度足够时进入已有声音组；不足时创建新组。
- 主人给代表样本打标签时，默认回写到整组，减少逐条判断负担。
- 误报也会作为一类声音组保留，用于后续降低类似声音的干扰。

## 4. 技术架构

### 4.1 前端采集

- `navigator.mediaDevices.getUserMedia({ audio: true })` 获取麦克风。
- Web Audio `AudioContext` + `AnalyserNode` 做实时能量、频谱和自适应噪声基线分析。
- 使用 Meyda 提取过零率、频谱质心、平坦度等浏览器端特征；不可用时回退到基础特征。
- 使用滑动窗口检测候选片段，例如短时间能量突增、频谱变化、重复脉冲。
- 使用 MediaRecorder 保存触发前后几秒音频。
- 先做端上粗筛，只上传候选片段，不做全程录音上传。

### 4.2 存储

当前已扩展数据模型：

- `BarkSample`：候选样本、音频地址、声学特征、embedding、波形、检测分数、人工标签和关联时间线事件。
- `BarkSession`：连续叫声段、开始/结束时间、代表样本、叫声次数、样本数量和关联时间线事件。
- `BarkCluster`：相似声音组、聚类中心、样本数、组标签和状态。
- `TimelineEvent`：继续保留 `BARK` 类型事件，并在 metadata 中关联 `barkSampleId`、`clusterId`、`audioUrl`、`detectorVersion` 和 `barkScore`。

音频文件不建议放 D1；短片段进入 R2，D1 只存 URL、特征、标签和索引。

### 4.3 模型路线

分三层推进：

- V1 本地启发式检测：响度、频谱、持续时间、重复脉冲，先解决“有没有叫”。
- V2 通用音频分类：引入预训练音频模型或服务端模型，区分狗叫、环境噪音、人声、门铃等。
- V3 个性化意图判断：结合音频 embedding、时间、喂食/外出/训练历史、主人反馈，预测“为什么叫”。
- V4 多模态判断：接入摄像头后，把姿态、位置、朝向、是否靠近门/食盆/主人等视觉线索与叫声向量融合。

深度学习模型不一定必须云端引入，推荐按数据量和算力分层部署：

- 端上轻模型：浏览器或 PWA 内运行 TensorFlow.js / ONNX Runtime Web，适合先做狗叫/人声/环境声粗分类。优点是隐私好、延迟低；缺点是手机耗电，模型体积和浏览器兼容性要控制。
- 云端推理：把候选短片段上传到自有 API 或 Cloudflare Worker 后端，再转给音频模型服务。优点是模型能力强、迭代快；缺点是音频隐私、成本和网络稳定性需要产品开关。
- 家用采集设备：树莓派、旧手机或小型边缘设备长期监听，设备端提取 embedding，只同步候选片段和特征。优点是能做锁屏/无人值守；缺点是硬件部署复杂。
- 个性化学习：先不急着端到端训练大模型，先收集 `BarkSample`、声纹 embedding、主人标签和处理结果。样本达到几十到几百条后，可以训练轻量分类头或相似度检索模型，用每只宠物自己的标签校准结果。

意图判断必须输出概率和解释，不输出确定性结论，例如：“更像是想出去，依据是晚间固定外出前 30 分钟、多次短促叫声、上次如厕已超过 3 小时。”

摄像头辅助不应替代主人校准。视觉模型同样只输出线索，例如“靠近门口”“朝向主人”“在食盆附近”“来回踱步”，最终仍结合时间、声音和反馈给概率判断。

当前仓库已提供本地模型同步脚本：

```bash
nvm use
npm run bark:model:download
npm run bark:model:train
npm run bark:model:push
```

`download` 会从远程 D1 下载 `BarkSample`、`BarkSession`、`BarkCluster`，并从 R2 拉取短音频到 `data/bark-sync/audio/`；`train` 会基于已标注样本训练轻量 nearest-centroid 模型；`push` 会把新的 `BarkModelArtifact` 写回远程 D1。`npm run bark:model:sync` 可以一键完成三步。

## 5. 隐私与安全

- 默认只保存触发片段，不保存连续环境录音。
- 采集页面必须显示麦克风正在工作。
- 支持一键暂停监听和删除音频。
- 默认不把原始音频发给第三方模型；如需云端分析，必须在设置中显式开启。
- 所有模型判断都标记为行为辅助分析，不能当作医疗或训练定论。

## 6. 推荐迭代顺序

1. 需求和数据模型：先把 `BARK` 事件类型、R2 音频片段和人工反馈表设计好。
2. 前台监听 MVP：做浏览器端麦克风监听、能量阈值、候选片段保存和时间线记录。
3. 校准闭环：做“确认/误报/原因标签/处理后是否停止”。
4. 图表分析：按时间段、场景、原因标签和处理动作统计狗叫规律。
5. 模型增强：引入音频 embedding 和服务端分类，逐步替换启发式规则。
6. 长期后台方案：评估 Expo/React Native 或家用采集设备，解决锁屏后台监听。

## 7. 暂不做

- 第一版不做锁屏后台永久监听承诺。
- 第一版不做医疗诊断或分离焦虑结论。
- 第一版不上传全天原始录音。
- 第一版不把“无聊/想吃/想出去”作为确定性答案，只作为概率建议和待校准标签。
